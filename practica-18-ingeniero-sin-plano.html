Práctica 18: Ingeniero sin plano

Práctica extra avanzada para interpretar arquitectura de circuito desde texto, resolver ambigüedad y justificar decisiones de diseño como en un problema real de ingeniería.

Volver al índice

Guía de trabajo

Nombre del reto: Ingeniero sin plano

Tipo de práctica: Extra avanzada

Nivel: Intermedio - Avanzado

Modalidad: Individual o por parejas

Duración estimada: 2 a 3 sesiones

En esta práctica no se entrega un diagrama. El alumno debe deducir las conexiones y justificar técnicamente su decisión. Los bloques de código incluyen botón de copia.

Propósito

Que el alumno sea capaz de interpretar la arquitectura de un circuito a partir de texto y lógica, diseñar conexiones sin diagrama, resolver ambigüedad como en problemas reales y relacionar hardware, software y comportamiento del sistema.

Nivel

Intermedio - Avanzado, ideal para CETis o bachillerato técnico.

Escenario del reto

Situación: Debes construir un sistema de control donde un botón cambie entre tres modos de comportamiento de un LED. No tienes diagrama, solo especificaciones técnicas.

Especificación técnica

El sistema debe cumplir con lo siguiente:

  • Existe un actuador luminoso conectado a un pin digital de salida.
  • Existe un dispositivo de entrada mecánico conectado a un pin digital.
  • El sistema debe evitar lecturas inestables, rebotes o ruido.
  • Se debe implementar lógica de cambio de estado por pulsación.

Restricciones del reto

Solo puedes usar:

  • 1 LED
  • 1 botón
  • Resistencias

No se permite diagrama.

No se te dice cómo conectar exactamente el botón.

El alumno debe decidir:

  • Si usa pull-up o pull-down.
  • Qué terminal va a GND y cuál va a 5V.
  • Dónde colocar la resistencia.

Código incompleto base

Este código no explica el circuito. El alumno debe interpretarlo y construir un sistema funcional a partir de él.

int led = 9;
int boton = 6;

int estado = 0;
bool ultimoEstado = LOW;

void setup() {
  pinMode(led, OUTPUT);
  pinMode(boton, INPUT);
}

void loop() {
  bool lectura = digitalRead(boton);

  if (lectura == HIGH && ultimoEstado == LOW) {
    estado++;
    if (estado > 2) estado = 0;
    delay(200);
  }

  ultimoEstado = lectura;

  if (estado == 0) {
    digitalWrite(led, LOW);
  } 
  else if (estado == 1) {
    digitalWrite(led, HIGH);
  } 
  else {
    digitalWrite(led, millis() % 500 < 250);
  }
}

Lo que el alumno debe deducir

1. Interpretación de hardware

  • ¿El botón está en HIGH cuando se presiona o cuando no?
  • ¿Necesita resistencia? ¿Dónde debe colocarse?
  • ¿Qué ocurre si no se usa resistencia?

2. Diseño del circuito

El alumno deberá decidir si resuelve el circuito con:

  • Pull-down clásico
  • Pull-up como solución más profesional

Ambas soluciones pueden aceptarse si están correctamente justificadas.

Planeación del alumno

Fase 1: Haz que funcione

El objetivo inicial es que el sistema logre los tres estados solicitados:

  • Estado 0: LED apagado
  • Estado 1: LED encendido
  • Estado 2: LED parpadeando

Fase 2: Explícame por qué funciona

Fase 3: ¿Cómo lo harías más profesional?

Ahora el alumno debe pensar como técnico o ingeniero, no solo como usuario de ejemplos.

Reto 2: Mantener estado al reiniciar

Sin cambiar componentes, modifica el sistema para que conserve el último estado aunque se reinicie el Arduino. Este reto lleva al uso de EEPROM.

#include <EEPROM.h>

int led = 9;
int boton = 6;
int estado = 0;
bool ultimoEstado = LOW;

void setup() {
  pinMode(led, OUTPUT);
  pinMode(boton, INPUT);
  estado = EEPROM.read(0);
  if (estado > 2) estado = 0;
}

void loop() {
  bool lectura = digitalRead(boton);

  if (lectura == HIGH && ultimoEstado == LOW) {
    estado++;
    if (estado > 2) estado = 0;
    EEPROM.update(0, estado);
    delay(200);
  }

  ultimoEstado = lectura;

  if (estado == 0) digitalWrite(led, LOW);
  else if (estado == 1) digitalWrite(led, HIGH);
  else digitalWrite(led, millis() % 500 < 250);
}

Reto 3: Modo especial por pulsación larga

Si el botón se mantiene presionado más de 2 segundos, el sistema entra en modo especial de parpadeo rápido. Aquí entran manejo de tiempo, lógica no bloqueante y programación embebida más real.

int led = 9;
int boton = 6;

int estado = 0;
bool ultimoEstado = LOW;
bool presionado = false;
bool modoEspecial = false;
unsigned long tiempoPresionado = 0;

void setup() {
  pinMode(led, OUTPUT);
  pinMode(boton, INPUT);
}

void loop() {
  bool lectura = digitalRead(boton);

  if (lectura == HIGH && !presionado) {
    presionado = true;
    tiempoPresionado = millis();
  }

  if (lectura == HIGH && presionado && millis() - tiempoPresionado >= 2000) {
    modoEspecial = true;
  }

  if (lectura == LOW && ultimoEstado == HIGH) {
    if (!modoEspecial) {
      estado++;
      if (estado > 2) estado = 0;
    }
    presionado = false;
    modoEspecial = false;
    delay(60);
  }

  ultimoEstado = lectura;

  if (modoEspecial) {
    digitalWrite(led, millis() % 120 < 60);
  } else if (estado == 0) {
    digitalWrite(led, LOW);
  } else if (estado == 1) {
    digitalWrite(led, HIGH);
  } else {
    digitalWrite(led, millis() % 500 < 250);
  }
}

Evaluación

  • Diseño correcto sin diagrama.
  • Justificación del tipo de conexión elegida.
  • Explicación de rebotes y ruido.
  • Código funcional.
  • Resolución de errores.
  • Nivel de autonomía durante el reto.

Tip didáctico

No se recomienda dar toda la información al mismo tiempo.

  1. Primero: haz que funcione.
  2. Después: explícame por qué funciona.
  3. Al final: ¿cómo lo harías más profesional?

Producto final del alumno

  • Descripción escrita de la conexión elegida.
  • Justificación técnica de pull-up o pull-down.
  • Código funcional del reto base.
  • Respuesta de análisis sobre rebotes, ruido y lógica de estados.
  • Resolución de al menos uno de los retos avanzados.
  • Conclusión personal sobre cómo pensó y resolvió el problema.

Conclusión

Esta práctica obliga al alumno a salir del modelo de seguir un diagrama fijo y lo acerca a una situación más real de ingeniería. El reto no consiste solo en conectar componentes, sino en interpretar especificaciones, decidir una arquitectura válida, justificarla y hacer que el sistema funcione de manera estable.
